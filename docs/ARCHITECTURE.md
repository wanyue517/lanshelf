# 技术架构与安全边界

## 1. 应用拓扑

每台运行 LanShelf 的电脑同时承担三种角色：

1. **桌面端**：Electron + Vue 负责悬浮 UI、交互及系统托盘。
2. **共享端**：Node HTTP 服务暴露已授权的文件列表与文件流。
3. **客户端**：mDNS 发现设备，用 WebSocket 接收更新，用 HTTP 拉取远端文件。

不需要独立部署 Spring Boot、Redis 或数据库服务器。首版每个设备存储自己的元数据与共享文件。

## 2. 代码层次

- `main.ts`：窗口生命周期、IPC 注册、对话框、原生拖出、开机自启。
- `preload.ts`：只暴露白名单 API，把 Drop 里的 File 对象解析为本机文件路径。
- `engine.ts`：托管文件/文件夹 ZIP、文本创建、缓存、打开、删除。
- `lan.ts`：Bonjour/mDNS、WS、HTTP、六位码配对、文件流。
- `store.ts`：本机设备 ID、文件目录索引、配对凭据及配置。
- `shared/types.ts`：IPC 契约和可见状态类型。

## 3. 设备发现

通过 DNS-SD/mDNS 注册 `_lanshelf._tcp.local`，TXT 包含设备 UUID 与可读名称。发现信息本身不代表可信。首次连接必须手工使用对方的配对码。

## 4. 配对协议（当前开发预览版）

1. A、B 通过 mDNS 看见对方。
2. A 显示 5 分钟轮换的 6 位码；B 手动输入 A 的码。
3. B 生成 32 字节随机入站令牌 B1，向 A 发起 POST `/pair`，携带自己的 ID、名字、B1 与配对码。
4. A 验证码（单 IP 错误请求限速）、生成 32 字节令牌 A1，并记录 A1 为来自 B 的入站令牌，B1 为访问 B 的出站令牌。
5. A 返回 A1，B 记录 B1 为来自 A 的入站令牌，A1 为访问 A 的出站令牌。
6. 双方后续访问 `/items`、`/file/:id` 与 `/ws` 使用对应的 Bearer Token。

**安全说明：当前传输为明文 HTTP/WebSocket，配对码和令牌可被同网段具备监听条件的攻击者截获。仅用于可信网络，不能视为生产安全实现。** 后续应更换为 TLS + 设备身份公钥绑定，在认证完成之前绝不暴露文件列表。

## 5. 同步机制

本机新增或删除文件时广播 `changed` WebSocket 消息；各个已配对对端通过 `GET /items` 拉取新快照。

来源设备离线后，不清除上次获得的文件索引，但将未缓存的远端文件标记不可用。重新上线后重新同步。

此模型为「每个设备只拥有自己创建的文件条目」的联合视图，不存在多人同时编辑同一文件元数据的问题。删除权限仅属于来源设备。

## 6. 文件传输与数据生命周期

- 拖入本机文件：异步复制到 `userData/files/{UUID}/`。
- 拖入目录：归档为 ZIP，再创建共享条目。
- 接收端第一次请求：通过已授权 HTTP 下载到 `userData/cache/` 临时文件，校验字节数后原子重命名。
- 再次请求：直接使用缓存，不重复下载。
- 另存为：经操作系统原生保存对话框复制缓存/源文件。
- 原生拖出：Electron `webContents.startDrag({ file, icon })`，要求有真实本地路径。

未实现：内容哈希、断点续传、下载缓存配额、自动 GC、链接级传输加密、并发限流。正式投入日常使用前需补上。

## 7. 威胁模型与工程约束

- 不在渲染层泄露文件路径或访问令牌。文件操作及 HTTP 请求由主进程执行。
- 只允许已授权的客户端访问列表及内容；远端无法凭文件名拼接任意本地路径。
- 文件名需要去除 Windows 保留字符与设备名；实际文件路径以 UUID 为目录隔离。
- 拖入的文件可能极大；当前托管复制占用本机磁盘，需后续提供空间上限。
- Windows 防火墙、AP 隔离、VLAN 可能影响 mDNS 或 TCP；需要清晰的 UI 错误提示。
- JSON 存储仅用于 MVP：后续可迁移 SQLite，做到事务、缓存索引和历史日志。
- 不应在缺乏授权的网络中使用；不能把「局域网」等同于「安全」。
